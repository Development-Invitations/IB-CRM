## 1. Согласованный стек

| Слой | Технология | Причина |
|---|---|---|
| Desktop-приложение | **Tauri 2 (Rust)** | ~3-10 МБ вместо 100+ МБ у Electron, меньше RAM, использует системный WebView; заменили Electron в v0.1.0 после сравнения |
| Frontend | React + TypeScript + Vite | быстро, без ожидания, богатая экосистема; код почти не изменился при переходе с Electron |
| Backend (заменено в v0.2.0, было ⏳ план Node.js + NestJS) | Embedded HTTP-сервер на `axum`/`tokio` внутри того же Rust-процесса Tauri | план на NestJS не был начат (0% кода/зависимостей); пользователю нужна "универсальная сборка", где сервером может быть обычный ПК без отдельной установки Node.js — соседний процесс не подходит, встроенный сервер в тот же бинарник подходит |
| БД | SQLite (rusqlite, из Rust-ядра) — используется и локально, и в режиме сервера (раздаётся по сети тем же процессом) | план на PostgreSQL (`docs/db/schema.sql`) отменён вместе с NestJS — схема файла осталась как справочная целевая, но не используется |
| Сеть клиент↔сервер (v0.2.0) | Обычный HTTP + токен сессии (`X-Session-Token`), без TLS | доверенная офисная LAN, пользователь явно выбрал вариант без сертификатов при планировании v0.2.0 |
| Real-time (план, не начато) | Socket.io / WebSocket | чаты в проектах, уведомления — сейчас poll через обычные HTTP-команды |
| Очереди/кэш (план, не начато) | Redis | движок авто-распределения задач |
| Авто-обновление приложения | `tauri-plugin-updater` — подключён и работает технически (v0.1.1), не активен без реального ключа подписи и опубликованных релизов | подтягивание новых версий с сервера/Git; у Tauri эта механика продумана лучше для приватных репозиториев, чем electron-updater "из коробки" |
| Иконки UI | lucide-react | чистые, ложатся на палитру логотипа |
| Иконка приложения | генерируется из `src-tauri/icons-source/logo.png` командой `npm run tauri:icon` | официальный инструмент Tauri, сам режет под все размеры/платформы |

> **Почему ушли с Electron:** тот же UI на React/Vite, но заметно легче установщик,
> ниже расход RAM, встроенная модель авто-обновления удобнее для приватного репозитория.
> Backend-логика (`electron/db.js` с better-sqlite3) переписана на Rust (`src-tauri/src/db.rs`
> с rusqlite) — SQL-запросы и структура таблиц идентичны, просто на другом языке.

## 4. Полная схема БД (целевая, для серверной версии)

Файл: `docs/db/schema.sql` (PostgreSQL). Покрывает все модули из таблицы выше.
В offline-прототипе v0.1.0 используется урезанная SQLite-версия только с таблицами
`employees` и `app_meta` (см. `electron/db.js`) — по мере появления сервера будет заменена.

## 5. Ключевые архитектурные решения (зафиксированы, не пересматривать без причины)

1. Регистрация сотрудника — только логин+пароль, без подтверждения почты; остальной
   профиль дозаполняется самим сотрудником в личном кабинете.
2. Права выдаются точечно через `employee_permissions`, а не жёстко зашиты в роль —
   админ может делегировать право "управлять должностями" одному или нескольким людям.
3. Передача "главенства" над проектом фиксируется историей (`project_ownership_transfers`),
   а не просто перезаписывает поле.
4. Авто- и ручное распределение задач — одна таблица `task_assignments`, разница только
   в `assignment_type` и наличии/отсутствии `assigned_by`.
5. Desktop-клиент на **Tauri** (Rust-ядро), а не веб-приложение в браузере — так как нужна
   установка "приложения" с сервера и авто-обновления, что явно требовалось. Изначально
   собрали прототип на Electron, но по запросу пользователя (нужнее лёгкий/современный вариант)
   перешли на Tauri — фронтенд на React сохранён почти без изменений, поменялось только ядро.
6. v0.1.0 сознательно офлайн (без сервера) — по прямому запросу, чтобы можно было
   протестировать базовый каркас до того, как поднимать бэкенд/сервер.

## 7. Журнал изменений

### v0.1.0 — offline-прототип, Tauri-версия (текущая)
- Инициализирован репозиторий, структура **Tauri 2 (Rust) + React + Vite + TypeScript**.
- Первая сборка была на Electron — по запросу пользователя пересобрана на Tauri:
  `electron/main.js` + `electron/db.js` (Node.js + better-sqlite3) заменены на
  `src-tauri/src/main.rs` + `src-tauri/src/db.rs` (Rust + rusqlite), логика и схема идентичны.
  Фронтенд почти не тронут — только `window.api.*` заменено на `src/lib/api.ts` (обёртка над `invoke`).
- Реализован первый запуск: создание администратора локально (SQLite, без сервера).
- Реализован вход по логину/паролю, чекбокс "запомнить меня" (UI, логика — заглушка).
- Каркас кабинета: сайдбар со всеми будущими модулями (помечены "скоро"), переключатель
  темы тёмная/светлая на палитре логотипа.
- Подключён исходник лого (`src-tauri/icons-source/logo.png`) для генерации иконки приложения
  через штатный `tauri icon`.
- Спроектирована и сохранена полная целевая схема PostgreSQL под все модули (`docs/db/schema.sql`).
- Итоговый зафиксированный стек: Tauri (Rust) + React + NestJS (план) + PostgreSQL (план) + Redis (план) + Socket.io (план).

### Фикс: недостающие иконки блокировали Windows-сборку
- При первом реальном запуске `tauri dev` сборка падала на этапе `build.rs`:
  `icons/icon.ico` not found — конфиг уже ссылался на иконки, которых физически не было
  (был только исходник в `icons-source/`).
- Сгенерировал набор `32x32.png`, `128x128.png`, `128x128@2x.png`, `icon.png`, `icon.ico`
  прямо из `logo.png` и положил в `src-tauri/icons/`.
- Убрал `icon.icns` из `tauri.conf.json` — нужен только для macOS-сборки, которой пока нет;
  когда дойдём до Mac-версии, надо будет сгенерировать через `npm run tauri:icon` на Mac
  (там есть системный `iconutil`, которого нет на этой машине) или через отдельный конвертер.

### Топбар, иконки, страница настроек, реальная смена пароля
- Добавлен `lucide-react`, иконки модулей в сайдбаре (Users, Building2, Contact, FolderKanban,
  FileText, MessageSquare, Cake, Server).
- Добавлен топбар (`src/components/Topbar.tsx`): заголовок-приветствие + иконка уведомлений

### v0.1.8 — багфиксы после локального тестирования 0.1.7 перед публикацией
Пользователь тестировал 0.1.7 локально перед заливкой на GitHub и обнаружил 4 проблемы.

- **Приложение "не закрывалось" по крестику** — реальная причина: обработчик закрытия окна

  процесс — он продолжает висеть в фоне невидимым. Заменил на `exit(0)` из

  обновления, так что доступность гарантирована) — это по-настоящему завершает процесс.

  зависнет по любой причине, закрытие окна всё равно произойдёт, а не будет ждать вечно.

  уведомлений один раз при монтировании и больше никогда не обновлял, пока компонент не

### v0.1.9 — уведомление не чистилось у остальных получателей после решения по заявке
Пользователь сначала случайно продублировал предыдущее сообщение (уточнил — отправил по
ошибке, версия 0.1.8 уже всё чинит), затем указал на реальный отдельный баг.

- **Причина**: заявку (на изменение данных или на отсутствие) могут увидеть сразу несколько
  человек — например, руководитель и его заместитель, либо все админы, если руководитель не
  назначен. У каждого получателя — своя отдельная строка в таблице `notifications` со своим
  `id`, но одинаковым `related_entity_id` (id самой заявки). `mark_notification_read`
  помечал прочитанной только ТУ строку, по которой кликнули — соответственно, если заявку
  обрабатывал, скажем, руководитель, у заместителя (или у прочих админов) непрочитанное
  уведомление оставалось висеть, хотя заявка уже была решена.
- **Фикс**: новый метод `mark_notifications_for_entity_read(related_entity_id)` в `db.rs` —
  помечает прочитанными ВСЕ уведомления с данным `related_entity_id`, независимо от
  получателя. Вызывается в конце и `resolve_edit_request`, и `resolve_absence_request`,
  сразу после того как заявка переведена в финальный статус. Уведомление о самом результате
  (новое, адресованное автору заявки — "заявка одобрена/отклонена") этой очисткой не
  затрагивается, у него `related_entity_id = None`, отдельная сущность.
- Дополнительных правок на фронтенде не потребовалось — опрос уведомлений раз в 10 секунд
  (добавлен в v0.1.8) сам подхватит очищенный статус у остальных получателей при следующем
  цикле опроса, без переоткрытия страницы.

### Фикс сборки: `failed to run light.exe` (WiX/MSI) — переключились на только-NSIS
Пользователь запустил `npm run tauri:build` первый раз после апгрейда конфига в v0.1.11.
Rust собрался успешно (`Finished release profile`, `.exe` готов), упало только на упаковке
в `.msi` — `failed to run C:\...\WixTools314\light.exe`. Это стандартная проблема Windows-
тулчейна WiX (набор, который Tauri сам скачивает для сборки MSI), почти всегда вызвана либо
повреждённой автозагрузкой WixTools, либо отсутствием .NET Framework 3.5 (обязателен для
`light.exe`, это старый .NET-инструмент) — никак не связана с изменениями в коде из v0.1.11.

Раз изначально просили именно NSIS-инсталлятор (на русском, с издателем) — решили не

### v0.2.0 — реальное подключение к серверу (embedded, план NestJS/PostgreSQL/Socket.io/Redis заменён)
Пользователь явно попросил собрать v0.2.0 "с подключением на сервер" и подчеркнул два жёстких
требования: приложение многопользовательское, и сервером должен уметь быть обычный один ПК
(без отдельной инфраструктуры) — а сборка должна быть одна универсальная, роль (сервер/клиент)
выбирается внутри приложения. Аспирационный стек из §1 (Node.js/NestJS + PostgreSQL + Socket.io +
Redis) на тот момент не имел ни строчки кода и ни одной зависимости — под эти два требования он
и не подходил (отдельный Node-процесс не даёт "один .exe = сервер или клиент"). Решение —
**embedded-сервер**: тот же Rust-процесс Tauri поднимает фоновый HTTP-сервер (`axum`), когда
включён "режим сервера"; SQLite остаётся единственной БД, просто теперь доступна по сети.
PostgreSQL-схема (`docs/db/schema.sql`) как справочный целевой документ не удалена, но больше не
является рабочим планом. Полный подход зафиксирован в плане Claude Code перед реализацией; ниже —
что реально сделано.

**Архитектура.** Все ~90 фронтенд-вызовов уже шли через один `invoke()` в `src/lib/api.ts` — это
и стало единственной точкой, которую нужно было сделать "сетеосознанной":
- **Локальный режим** (по умолчанию, как в v0.1.x) — без изменений, `invoke()` идёт через
  `@tauri-apps/api/core` в тот же процесс.
- **Режим сервера** — тот же локальный режим плюс фоновый axum-сервер на `0.0.0.0:<порт>`
  (по умолчанию 8778), поднимается в `main.rs` `.setup()`, если в `app_meta` включён
  `server_enabled`. Управляется тумблером в Настройках (только админ) — новые команды
  `get_server_settings`/`set_server_settings` (`src-tauri/src/db.rs`, `main.rs`).
- **Режим клиента** — `invoke()` в `api.ts` вместо Tauri IPC делает HTTP-запрос на
  `${serverUrl}/api/invoke` через `@tauri-apps/plugin-http` (официальный плагин Tauri для сети
  за пределами webview — голый `fetch` в webview ограничен CSP). Куда подключаться — хранится в
  `localStorage` (новый `src/lib/connection.ts`), доступно ещё до логина.
- **Общий код, не дублирование.** Новый `src-tauri/src/dispatch.rs` — один диспетчер
  (`pub fn dispatch(cmd, payload, db) -> Result<Value, String>`), match на все ~90 команд,
  каждая ветка десериализует тот же `XPayload`, что и одноимённая Tauri-команда в `main.rs`, и
  вызывает тот же метод `Db`. Это стало возможным без объявления полусотни структур `pub`,
  потому что в Rust приватные items корня крейта (`main.rs`) уже видны дочерним модулям
  (`mod dispatch;`) без `pub(crate)` — неожиданная, но удобная находка.
- **Общее состояние.** `AppState` в `main.rs` — теперь `Arc<Mutex<Db>>` вместо `Mutex<Db>`, чтобы
  и Tauri-команды, и axum-роутер (`src-tauri/src/server.rs`) держали одну и ту же БД без второго
  подключения к файлу; `.lock()` во всех ~90 существующих команд не изменился (`Deref`).
- **Авторизация обязательна.** До сети `actor_id`/`admin_id` в теле команды был доверенным по
  факту (тот же локальный процесс). По сети это дыра — поэтому `server.rs` минтит
  UUID-токен на успешный `login`/`create_admin`, требует `X-Session-Token` на все прочие команды
  (401 при отсутствии/невалидности), и дополнительно сверяет любое поле `actorId`/`adminId`/
  `employeeId` в теле запроса с владельцем токена (нельзя прислать чужой id, даже будучи
  залогиненным). `record_logout` инвалидирует токен.
- **Требование связи, не офлайн-кэш.** По прямому выбору пользователя (через уточняющий вопрос
  при планировании) — клиент без связи с сервером не работает "вслепую", `api.ts` кидает понятную
  ошибку ("Нет соединения с сервером") вместо тихого залипания или устаревших данных.
- LAN IP сервера для показа админу — классический трюк `UdpSocket::connect("8.8.8.8:80")` +
  `local_addr()`, без новых зависимостей и без реального сетевого трафика (`get_lan_address`).

**Новые/изменённые файлы:** `src-tauri/src/server.rs` (новый, axum-роутер + CORS + токены),
`src-tauri/src/dispatch.rs` (новый, ~90 match-веток), `src-tauri/src/db.rs`
(`get_server_settings`/`set_server_settings` поверх `app_meta`), `src-tauri/src/main.rs`
(`AppState` на `Arc`, спавн сервера в `.setup()`, 3 новые команды), `src-tauri/Cargo.toml`
(`axum`, `tokio`, `tower-http`), `src-tauri/capabilities/default.json` (`http:default` с широким
URL-скоупом под LAN), `package.json` (`@tauri-apps/plugin-http`), `src/lib/connection.ts` (новый —
режим/адрес сервера в `localStorage`, токен сессии в `sessionStorage`, не переживает перезапуск —
тот же принцип, что уже был у `session.ts`), `src/lib/api.ts` (`invoke()` стал
сетеосознанным, ~90 функций `api.xxx()` не тронуты), `src/pages/FirstRunSetup.tsx` (переделан в
3-шаговый флоу: выбор локально/сервер → ввод адреса → создание/проверка админа),
`src/pages/Settings.tsx` (новая секция "Сервер" — на клиенте показывает адрес и кнопку
отключиться, на сервере/локали админу — тумблер, порт, LAN-адрес с копированием),
`src/pages/Dashboard.tsx` (убран отключённый пункт сайдбара "Подключение к серверу" с бейджем
"v0.2.0" — функциональность теперь в Настройках, доступных через шестерёнку в топбаре как и
раньше), i18n (`firstRun.*`, `settings.server.*` на всех 3 языках).

Не проверено вживую — `tsc --noEmit`, `cargo check --no-default-features`, `vite build` чистые
(zero warnings по Rust-части, включая ~90 диспетчерских веток с первой попытки после одной
опечатки в сигнатуре вызова). Реальный двухпроцессный LAN-тест (поднять сервер на одном
запущенном экземпляре, подключиться вторым с другого IP/порта, создать данные с одного — увидеть
с другого) не выполнялся в рамках этой сессии. Также не проверено вживую: поведение Windows
Firewall при первом включении режима сервера (ОС должна спросить разрешение на входящие
подключения — это ожидаемо, не баг, но стоит убедиться на реальной машине), и что
`@tauri-apps/plugin-http` действительно обходит CSP для произвольных LAN-адресов (permissions
выставлены по образцу `permissions/default.toml` пакета, но не запускались).

### v0.2.1 — модалки (Esc/крестик/клик-вне) + починка навигации уведомлений
Пользователь прислал два скриншота модалки создания/редактирования темы блога (тесный редактор) и
попросил: расширить эту модалку для добавления и редактирования, а также сделать так, чтобы ВСЕ
модальные окна закрывались по крестику, клику вне окна и клавише Esc — плюс общая просьба
проверить уведомления по всему приложению и поправить функционал.

- **`Modal.tsx`** (единственный переиспользуемый компонент модалок, используется во всех ~20
  местах в проекте — все они правятся этим одним изменением): добавлен `useEffect` с обработчиком
  `keydown` на `Escape` → `onClose()` (навешивается только пока `open`); добавлена кнопка-крестик
  (`X` из lucide-react, `.modal-close`, абсолютно спозиционирована в правом верхнем углу). Клик
  вне окна уже работал (`onMouseDown` на backdrop, если `e.target === e.currentTarget`) — не
  трогали. Добавлен опциональный проп `size?: 'lg'` → класс `.modal-card-lg` (860px вместо
  460px), для форм с `RichEditor`, которым тесно в стандартной ширине.
- **CSS**: `.modal-card` получил `position: relative` (нужно для абсолютного позиционирования
  крестика) — проверено, что это не ломает позиционирование других `position: absolute` элементов
  внутри модалок (у всех остальных — `.custom-select-menu`, `.rich-editor-color-popover`,
  `.reg-lightbox-close` и т.д. — уже есть свой ближайший `position: relative`/`fixed` родитель,
  так что общий `position: relative` у `.modal-card` их не задевает). `.modal-title` получил
  больше `padding-right` (26px → 40px), чтобы длинный заголовок не наезжал на крестик.
- **Блог — широкая модалка**: `size="lg"` добавлен на оба места создания/редактирования темы
  (полноэкранный вид и список тем — та же пара мест, где в v0.1.22 был баг с двумя похожими
  формами). Плюс `.modal-card-lg .rich-editor-content` — увеличенная высота текстовой области
  (180px → 320px мин., до 55vh макс.) специально в широкой модалке.

  `navigate(/dashboard/employees/:id)` — то есть клик по уведомлению "вам назначена задача в
  регламенте" или "вам передали проект" вёл в собственный кабинет сотрудника, а не туда, где
  реально что-то произошло. Поправлено: теперь роутинг идёт по `n.relatedEntityType`

  `navigate('/dashboard/projects', { state: { openProjectId } })`, `birthday` отдельно ведёт в
