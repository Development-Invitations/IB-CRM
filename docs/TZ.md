## 1. Согласованный стек

| Слой | Технология | Причина |
|---|---|---|
| Desktop-приложение | **Tauri 2 (Rust)** | ~3-10 МБ вместо 100+ МБ у Electron, меньше RAM, использует системный WebView; заменили Electron в v0.1.0 после сравнения |
| Frontend | React + TypeScript + Vite | быстро, без ожидания, богатая экосистема; код почти не изменился при переходе с Electron |
| Backend (заменено в v0.2.0, было ⏳ план Node.js + NestJS) | Embedded HTTP-сервер на `axum`/`tokio` внутри того же Rust-процесса Tauri | план на NestJS не был начат (0% кода/зависимостей); пользователю нужна "универсальная сборка", где сервером может быть обычный ПК без отдельной установки Node.js — соседний процесс не подходит, встроенный сервер в тот же бинарник подходит |
| БД | SQLite (rusqlite, из Rust-ядра) — используется и локально, и в режиме сервера (раздаётся по сети тем же процессом) | план на PostgreSQL (`docs/db/schema.sql`) отменён вместе с NestJS — схема файла осталась как справочная целевая, но не используется |
| Сеть клиент↔сервер (v0.2.0) | Обычный HTTP + токен сессии (`X-Session-Token`), без TLS | доверенная офисная LAN, пользователь явно выбрал вариант без сертификатов при планировании v0.2.0 |
| Real-time (план, не начато) | Socket.io / WebSocket | чаты в проектах, уведомления — сейчас poll через обычные HTTP-команды |
| Очереди/кэш (план, не начато) | Redis | движок авто-распределения задач |
| Авто-обновление приложения | `tauri-plugin-updater` — подключён и работает технически (v0.1.1), не активен без реального ключа подписи и опубликованных релизов | подтягивание новых версий с сервера/Git; у Tauri эта механика продумана лучше для приватных репозиториев, чем electron-updater "из коробки" |
| Иконки UI | lucide-react | чистые, ложатся на палитру логотипа |
| Иконка приложения | генерируется из `src-tauri/icons-source/logo.png` командой `npm run tauri:icon` | официальный инструмент Tauri, сам режет под все размеры/платформы |

> **Почему ушли с Electron:** тот же UI на React/Vite, но заметно легче установщик,
> ниже расход RAM, встроенная модель авто-обновления удобнее для приватного репозитория.
> Backend-логика (`electron/db.js` с better-sqlite3) переписана на Rust (`src-tauri/src/db.rs`
> с rusqlite) — SQL-запросы и структура таблиц идентичны, просто на другом языке.

## 4. Полная схема БД (целевая, для серверной версии)

Файл: `docs/db/schema.sql` (PostgreSQL). Покрывает все модули из таблицы выше.
В offline-прототипе v0.1.0 используется урезанная SQLite-версия только с таблицами
`employees` и `app_meta` (см. `electron/db.js`) — по мере появления сервера будет заменена.

## 5. Ключевые архитектурные решения (зафиксированы, не пересматривать без причины)

1. Регистрация сотрудника — только логин+пароль, без подтверждения почты; остальной
   профиль дозаполняется самим сотрудником в личном кабинете.
2. Права выдаются точечно через `employee_permissions`, а не жёстко зашиты в роль —
   админ может делегировать право "управлять должностями" одному или нескольким людям.
3. Передача "главенства" над проектом фиксируется историей (`project_ownership_transfers`),
   а не просто перезаписывает поле.
4. Авто- и ручное распределение задач — одна таблица `task_assignments`, разница только
   в `assignment_type` и наличии/отсутствии `assigned_by`.
5. Desktop-клиент на **Tauri** (Rust-ядро), а не веб-приложение в браузере — так как нужна
   установка "приложения" с сервера и авто-обновления, что явно требовалось. Изначально
   собрали прототип на Electron, но по запросу пользователя (нужнее лёгкий/современный вариант)
   перешли на Tauri — фронтенд на React сохранён почти без изменений, поменялось только ядро.
6. v0.1.0 сознательно офлайн (без сервера) — по прямому запросу, чтобы можно было
   протестировать базовый каркас до того, как поднимать бэкенд/сервер.

## 6. Открытые вопросы (нужно решение пользователя)

- Финальный список 4-5 дополнительных тем оформления (сейчас есть только тёмная/светлая).
- Векторный (SVG) вариант лого пригодился бы для splash-экрана и маркетинговых материалов —

  и работают на нём нормально, острой необходимости в SVG для текущих задач нет.
- Алгоритм авто-распределения задач: какие именно параметры учитывать (только текущая
  загрузка или ещё квалификация/специализация/приоритет клиента)?
- Где физически будет стоять сервер (свой VPS / облако) — нужно для модуля "подключение
  к серверу" и генерации ссылки на скачивание приложения сотрудникам.
- Формат авто-обновления: через приватный GitHub Releases репозитория IB-CRM, или через
  отдельный self-hosted update-сервер (важно, т.к. репозиторий приватный, а electron-updater
  по умолчанию рассчитан на публичные/токенизированные релизы).

## 7. Журнал изменений

### v0.1.0 — offline-прототип, Tauri-версия (текущая)
- Инициализирован репозиторий, структура **Tauri 2 (Rust) + React + Vite + TypeScript**.
- Первая сборка была на Electron — по запросу пользователя пересобрана на Tauri:
  `electron/main.js` + `electron/db.js` (Node.js + better-sqlite3) заменены на
  `src-tauri/src/main.rs` + `src-tauri/src/db.rs` (Rust + rusqlite), логика и схема идентичны.

### v0.1.8 — багфиксы после локального тестирования 0.1.7 перед публикацией
Пользователь тестировал 0.1.7 локально перед заливкой на GitHub и обнаружил 4 проблемы.
Версия поднята до 0.1.8 (та же предрелизная проверка, ещё не опубликовано).

- **Приложение "не закрывалось" по крестику** — реальная причина: обработчик закрытия окна
  в `App.tsx` использовал `getCurrentWindow().destroy()` после записи выхода
  (`api.recordLogout`). `destroy()` в некоторых случаях лишь скрывает окно, не завершая сам
  процесс — он продолжает висеть в фоне невидимым. Заменил на `exit(0)` из
  `@tauri-apps/plugin-process` (тот же пакет уже использовался для `relaunch()` после
  обновления, так что доступность гарантирована) — это по-настоящему завершает процесс.
  Заодно обернул `api.recordLogout` в `Promise.race` с таймаутом 1 секунда — если Rust-команда
  зависнет по любой причине, закрытие окна всё равно произойдёт, а не будет ждать вечно.
- **Уведомления о заявках приходили только после перезагрузки** — `Topbar.tsx` грузил список
  уведомлений один раз при монтировании и больше никогда не обновлял, пока компонент не
  перемонтируется (переход по страницам). Добавил `setInterval` на 10 секунд + принудительное
  обновление списка при каждом клике на колокольчик (перед открытием панели) — руководитель
  или админ теперь видят новую заявку в течение 10 секунд без необходимости что-либо
  перезагружать.
- **Не было возможности убрать сотрудника из подразделения** — только добавить/перевести.
  Добавил кнопку (иконка ×) рядом с каждым сотрудником в списке состава подразделения

- **Автообновление перезапускало приложение мгновенно, без единого сообщения** — выглядело
  так, будто программа просто вылетела, а не завершила обновление. Убрал `await relaunch()`

  уведомление, и `UpdatesButton.tsx` — ручная кнопка "Проверить обновления"), теперь после

  анимация появления) и только потом вызывают `restartApp()`.
- **Полный аудит на баги** — прогнал: 0 отсутствующих ключей перевода на все 3 языка;
  баланс скобок сошёлся во всех `.ts`/`.tsx`/`.css`/`.rs` файлах; отдельно проверил на

  `main.rs` (`invoke_handler`) в обе стороны скриптом — ни одной лишней или отсутствующей

### v0.1.9 — уведомление не чистилось у остальных получателей после решения по заявке
Пользователь сначала случайно продублировал предыдущее сообщение (уточнил — отправил по
ошибке, версия 0.1.8 уже всё чинит), затем указал на реальный отдельный баг.

- **Причина**: заявку (на изменение данных или на отсутствие) могут увидеть сразу несколько
  человек — например, руководитель и его заместитель, либо все админы, если руководитель не
  назначен. У каждого получателя — своя отдельная строка в таблице `notifications` со своим
  `id`, но одинаковым `related_entity_id` (id самой заявки). `mark_notification_read`
  помечал прочитанной только ТУ строку, по которой кликнули — соответственно, если заявку
  обрабатывал, скажем, руководитель, у заместителя (или у прочих админов) непрочитанное
  уведомление оставалось висеть, хотя заявка уже была решена.
- **Фикс**: новый метод `mark_notifications_for_entity_read(related_entity_id)` в `db.rs` —
  помечает прочитанными ВСЕ уведомления с данным `related_entity_id`, независимо от
  получателя. Вызывается в конце и `resolve_edit_request`, и `resolve_absence_request`,
  сразу после того как заявка переведена в финальный статус. Уведомление о самом результате
  (новое, адресованное автору заявки — "заявка одобрена/отклонена") этой очисткой не
  затрагивается, у него `related_entity_id = None`, отдельная сущность.
- Дополнительных правок на фронтенде не потребовалось — опрос уведомлений раз в 10 секунд
  (добавлен в v0.1.8) сам подхватит очищенный статус у остальных получателей при следующем
  цикле опроса, без переоткрытия страницы.

### v0.1.10 — ретроактивная чистка уведомлений, лоадер при проверке, диагноз проблемы с автообновлением
Пользователь протестировал v0.1.9 после реальной публикации на GitHub и сообщил три вещи.
Две из них — реальные баги в коде, поправлены; третья — не баг, а неправильный способ
публикации релиза.

- **Старые уведомления "висели" даже после фикса из v0.1.9** — причина в том, что фикс
  v0.1.9 (`mark_notifications_for_entity_read`) применяется только к заявкам, которые
  решаются ПОСЛЕ обновления. Заявки, обработанные в более ранних тестах (когда такой логики
  вообще не было), остались с непрочитанными уведомлениями в базе — фикс не ретроактивный
  сам по себе. Добавил разовую (но безвредную при каждом повторном запуске) чистку прямо в
  `init()`: при старте приложения все уведомления, у которых `related_entity_id` указывает
  на уже не-`pending` заявку (изменение данных ИЛИ отсутствие), помечаются прочитанными.
- **"Нет красивого лоадера при проверке"** — кнопка "Проверить обновления на сервере"
  показывала только текст "Проверка…" без единого визуального индикатора. Добавил: иконка
  на кнопке крутится (`.spin`, CSS-анимация), и под кнопкой на время проверки появляется
  компактный `<LoadingScreen compact />` (тот же пульсирующий логотип, что и на первом
  экране приложения) — теперь визуально понятно, что что-то происходит, а не просто ничего
  не откликается. В `UpdateNotifier.tsx` (авто-уведомление о новой версии) прогресс-бар и
  состояние "Готово!" уже были сделаны красиво в v0.1.8 — там ничего не потребовалось.
- **Обновление не находится после публикации релиза — НЕ баг, диагностировано через
  уточняющий вопрос**: пользователь подтвердил, что создавал релиз ВРУЧНУЮ на сайте GitHub
  и заливал файлы сам, а не через git-тег, который запускает `.github/workflows/release.yml`.
  При ручной загрузке в релизе нет ни подписанного установщика, ни файла `latest.json` —
  именно их обновлятор Tauri ищет по адресу из `endpoints` в `tauri.conf.json`. Без них
  проверка всегда будет молча возвращать "не найдено" (это ожидаемое, безопасное поведение
  — не должно ломать офлайн-режим, если сервер обновлений не настроен, см. запись про
  v0.1.1). **Правильный способ**: закоммитить, запушить и создать git-тег вида `vX.Y.Z`
  (`git tag v0.1.10 && git push origin v0.1.10`) — тогда GitHub Actions сам соберёт,
  подпишет и опубликует релиз со всем необходимым. Старый вручную созданный релиз стоит
  удалить, чтобы не путал.

### Фикс сборки: `failed to run light.exe` (WiX/MSI) — переключились на только-NSIS
Пользователь запустил `npm run tauri:build` первый раз после апгрейда конфига в v0.1.11.
Rust собрался успешно (`Finished release profile`, `.exe` готов), упало только на упаковке
в `.msi` — `failed to run C:\...\WixTools314\light.exe`. Это стандартная проблема Windows-
тулчейна WiX (набор, который Tauri сам скачивает для сборки MSI), почти всегда вызвана либо
повреждённой автозагрузкой WixTools, либо отсутствием .NET Framework 3.5 (обязателен для
`light.exe`, это старый .NET-инструмент) — никак не связана с изменениями в коде из v0.1.11.

Раз изначально просили именно NSIS-инсталлятор (на русском, с издателем) — решили не
бороться с WiX вообще: `bundle.targets` изменён с `"all"` на `["nsis"]` в
`tauri.conf.json`. NSIS — современный стандарт для Tauri, не требует .NET Framework 3.5,
и `bundle.windows.nsis.languages: ["Russian"]` из прошлой правки относится именно к нему.
Версию не поднимал — это чисто конфиг сборки, пользователь ещё не подтвердил успешную
сборку с этим фиксом.

Если когда-нибудь понадобится и MSI (например, для развёртывания через групповые политики
в организации) — можно будет вернуть `"targets": "all"`, но тогда на машине, где собирается
приложение, нужно будет включить .NET Framework 3.5 (Панель управления → Программы →
Включение или отключение компонентов Windows) и/или заново скачать WixTools, удалив
`%LOCALAPPDATA%\tauri\WixTools314` перед следующей сборкой.

### v0.2.0 — реальное подключение к серверу (embedded, план NestJS/PostgreSQL/Socket.io/Redis заменён)
Пользователь явно попросил собрать v0.2.0 "с подключением на сервер" и подчеркнул два жёстких
требования: приложение многопользовательское, и сервером должен уметь быть обычный один ПК
(без отдельной инфраструктуры) — а сборка должна быть одна универсальная, роль (сервер/клиент)
выбирается внутри приложения. Аспирационный стек из §1 (Node.js/NestJS + PostgreSQL + Socket.io +
Redis) на тот момент не имел ни строчки кода и ни одной зависимости — под эти два требования он
и не подходил (отдельный Node-процесс не даёт "один .exe = сервер или клиент"). Решение —
**embedded-сервер**: тот же Rust-процесс Tauri поднимает фоновый HTTP-сервер (`axum`), когда
включён "режим сервера"; SQLite остаётся единственной БД, просто теперь доступна по сети.
PostgreSQL-схема (`docs/db/schema.sql`) как справочный целевой документ не удалена, но больше не
является рабочим планом. Полный подход зафиксирован в плане Claude Code перед реализацией; ниже —
что реально сделано.

**Архитектура.** Все ~90 фронтенд-вызовов уже шли через один `invoke()` в `src/lib/api.ts` — это
и стало единственной точкой, которую нужно было сделать "сетеосознанной":
- **Локальный режим** (по умолчанию, как в v0.1.x) — без изменений, `invoke()` идёт через
  `@tauri-apps/api/core` в тот же процесс.
- **Режим сервера** — тот же локальный режим плюс фоновый axum-сервер на `0.0.0.0:<порт>`
  (по умолчанию 8778), поднимается в `main.rs` `.setup()`, если в `app_meta` включён
  `server_enabled`. Управляется тумблером в Настройках (только админ) — новые команды
  `get_server_settings`/`set_server_settings` (`src-tauri/src/db.rs`, `main.rs`).
- **Режим клиента** — `invoke()` в `api.ts` вместо Tauri IPC делает HTTP-запрос на
  `${serverUrl}/api/invoke` через `@tauri-apps/plugin-http` (официальный плагин Tauri для сети
  за пределами webview — голый `fetch` в webview ограничен CSP). Куда подключаться — хранится в
  `localStorage` (новый `src/lib/connection.ts`), доступно ещё до логина.
- **Общий код, не дублирование.** Новый `src-tauri/src/dispatch.rs` — один диспетчер
  (`pub fn dispatch(cmd, payload, db) -> Result<Value, String>`), match на все ~90 команд,
  каждая ветка десериализует тот же `XPayload`, что и одноимённая Tauri-команда в `main.rs`, и
  вызывает тот же метод `Db`. Это стало возможным без объявления полусотни структур `pub`,
  потому что в Rust приватные items корня крейта (`main.rs`) уже видны дочерним модулям
  (`mod dispatch;`) без `pub(crate)` — неожиданная, но удобная находка.
- **Общее состояние.** `AppState` в `main.rs` — теперь `Arc<Mutex<Db>>` вместо `Mutex<Db>`, чтобы
  и Tauri-команды, и axum-роутер (`src-tauri/src/server.rs`) держали одну и ту же БД без второго
  подключения к файлу; `.lock()` во всех ~90 существующих команд не изменился (`Deref`).
- **Авторизация обязательна.** До сети `actor_id`/`admin_id` в теле команды был доверенным по
  факту (тот же локальный процесс). По сети это дыра — поэтому `server.rs` минтит
  UUID-токен на успешный `login`/`create_admin`, требует `X-Session-Token` на все прочие команды
  (401 при отсутствии/невалидности), и дополнительно сверяет любое поле `actorId`/`adminId`/
  `employeeId` в теле запроса с владельцем токена (нельзя прислать чужой id, даже будучи
  залогиненным). `record_logout` инвалидирует токен.
- **Требование связи, не офлайн-кэш.** По прямому выбору пользователя (через уточняющий вопрос
  при планировании) — клиент без связи с сервером не работает "вслепую", `api.ts` кидает понятную
  ошибку ("Нет соединения с сервером") вместо тихого залипания или устаревших данных.
- LAN IP сервера для показа админу — классический трюк `UdpSocket::connect("8.8.8.8:80")` +
  `local_addr()`, без новых зависимостей и без реального сетевого трафика (`get_lan_address`).

**Новые/изменённые файлы:** `src-tauri/src/server.rs` (новый, axum-роутер + CORS + токены),
`src-tauri/src/dispatch.rs` (новый, ~90 match-веток), `src-tauri/src/db.rs`
(`get_server_settings`/`set_server_settings` поверх `app_meta`), `src-tauri/src/main.rs`

### v0.2.2 — подключение к серверу из уже установленного приложения (не только при первой установке)
Пользователь спросил "как правильно подключить приложение" применительно к реальному плану:
один мощный ноутбук становится сервером (со своими уже существующими локальными данными — их
не нужно никуда переносить, режим сервера просто открывает доступ к той же локальной базе по
сети), остальные ПК должны "подтягивать" данные с него. При проверке вскрылся пробел: экран
выбора "локально / подключиться к серверу" показывается только в `FirstRunSetup.tsx`, а он
рендерится в `App.tsx` только когда `!adminExists`, т.е. только при самой первой установке, когда
на устройстве ещё нет ни одного локального администратора. Ни один уже установленный и хоть раз
запущенный экземпляр приложения (а значит — почти наверняка каждый ПК сотрудника, раз приложение
уже в реальном использовании) не имел никакого способа переключиться в клиентский режим через UI.

- **`src/pages/Settings.tsx`** — добавлена секция "Подключиться к серверу", видна любому
  пользователю (не только админу), когда устройство ещё не в клиентском режиме (`!isClient`).
  Поле ввода адреса + кнопка "Подключиться" → `handleConnectToServer`: нормализует адрес (если
  нет `http://`/`https://` — подставляет `http://`), сразу переключает `connection` в клиентский
  режим (`connection.connectToServer`), затем пробует `api.hasAdmin()` — раз `invoke()` в `api.ts`
  уже сетеосознан, этот вызов реально бьёт на новый адрес и служит проверкой доступности. Если
  сервер ответил — очищает `session` (см. ниже, почему это обязательно) и делает
  `window.location.reload()`; если бросило исключение — откатывает через `connection.useLocal()`
  и показывает тост с ошибкой, режим клиента не остаётся "наполовину включённым".
- **Важный нюанс с `session.ts`**: сессия сотрудника (`sessionStorage`, переживает `reload()` в
  рамках одного открытого окна — см. комментарий в `session.ts`) хранит объект `Employee` с
  локальным ID. Если просто переключить режим и перезагрузить страницу без очистки этой сессии,
  `App.tsx` восстановил бы "залогиненного" сотрудника из старой локальной сессии и попытался бы
  сразу открыть `/dashboard` — но токена для этого сотрудника на новом сервере не существует,
  и первый же сетевой запрос упал бы с 401. Поэтому `handleConnectToServer` обязательно вызывает
  `session.clear()` перед `reload()` — после переключения на сервер честно показывается экран
  входа, и логиниться нужно уже под учётной записью, которая существует на сервере.
- Своя локальная база устройства при этом никуда не удаляется и не портится — просто перестаёт
  использоваться, пока подключение к серверу активно (симметрично уже существовавшей кнопке
  "Отключиться от сервера", которая возвращает в локальный режим тем же способом — `useLocal()`
  + `reload()`).
- Новые ключи i18n (все 3 языка): `settings.server.connectSectionTitle`,
  `settings.server.connectSectionHint` — остальные строки (`firstRun.serverUrlLabel`,
  `firstRun.connectBusy`, `firstRun.connectSubmit`, `firstRun.serverUnreachable`) переиспользованы
  из уже существующих ключей `FirstRunSetup.tsx`, чтобы не плодить дубли одного и того же смысла.

Не проверено вживую — `tsc`/`vite build` чистые (Rust не менялся в этой правке, `cargo check` не
перезапускался отдельно, т.к. изменений в `src-tauri/` не было). Стоит проверить: сценарий именно
из вопроса пользователя — включить сервер на ноутбуке (уже с реальными данными), с другого ПК,
где приложение уже использовалось локально, зайти в Настройки → "Подключиться к серверу", ввести
адрес и убедиться, что после перезагрузки действительно просит логин от сервера, а не зависает
и не путает локальную/серверную сессию.

**Обновление — проверено вживую в этой же сессии.** Пользователь реально прошёл весь сценарий на
двух физических устройствах: ноутбук стал сервером (обнаружился нюанс — сеть Wi-Fi была в профиле
"Public" в Windows, из-за чего firewall тихо блокировал входящие подключения без явной ошибки;
решилось явным правилом `New-NetFirewallRule ... -Profile Any` через PowerShell от администратора),
второе устройство подключилось как клиент через "Подключиться к серверу" в Настройках и успешно
вошло под учётной записью, реально существующей только на сервере (`EMP-00002`, "Азамов Фаррух") —
профиль, дата рождения, телефон и т.д. подтянулись именно с сервера, не из локальной копии.
Клиент-серверная связка подтверждена рабочей на реальном оборудовании, а не только по чистой
сборке.

### v0.2.4 — критичный баг режима сервера + доступ к чужим тредам + deep-link на задачу
Пользователь начал реальное двухпользовательское тестирование (сервер на одном ноутбуке, клиент
на другом, см. проверенный сценарий в записи v0.2.2) и практически сразу нашёл настоящий,
серьёзный баг — не мог добавить сотрудника в регламент/проект, и открытие чужого "кабинета"
зависало на загрузке навсегда. В процессе разбора всплыло ещё несколько связанных проблем.

- **Критичный баг: анти-спуфинг проверка в `server.rs` ложно блокировала обычные админские
  действия.** `ACTOR_FIELDS` включал `employeeId` в список полей, которые ДОЛЖНЫ совпадать с
  владельцем токена (сделано в v0.2.0 против подмены чужого id). Но `employeeId` в разных
  командах означает РАЗНОЕ: иногда это сам вызывающий (self-service), а иногда — цель чужого
  действия (кого добавить в регламент, кому админ правит профиль). Любое действие "админ/владелец
  над ДРУГИМ сотрудником" получало 403, потому что `employeeId` цели ≠ id вызывающего. Это ломало:
  добавление участника в регламент/проект, и — что важнее и незаметнее — открытие чужого профиля
  (`EmployeeProfile.tsx` дёргает `listRecentSessions(id)`/`listAbsenceRequestsForEmployee(id)` с
  ЧУЖИМ id), что и давало "вечную загрузку" при попытке зайти в чужой кабинет. Исправлено: из
  `ACTOR_FIELDS` убран `employeeId`, оставлены только `actorId`/`adminId` (эти имена по всей
  кодовой базе последовательно означают именно актёра). Добавлен отдельный узкий список
  `SELF_EMPLOYEE_ID_COMMANDS` (`self_update_employee`, `update_own_avatar`,
  `create_absence_request`, `create_edit_request`) — только для них `employeeId` дополнительно
  сверяется с токеном, т.к. там это поле действительно означает "сам вызывающий".
- **Второй системный баг, найденный в процессе: реальный текст ошибки терялся в клиентском
  режиме.** `api.ts`'s `invoke()` в клиентском режиме кидал `new Error(...)`, а весь остальной код
  проекта (все catch-блоки) писан под конвенцию локального Tauri IPC, где ошибка Rust-команды
  приходит в JS голой строкой. `typeof err === 'string'` не находил строку внутри `Error`-объекта
  и everywhere показывал общий фоллбэк ("Не удалось сохранить регламент" вместо реальной причины)
  — это и была надпись на скриншоте пользователя. Поправлено: клиентский `invoke()` теперь кидает
  голую строку (`throw result.error`), как и локальный IPC.
- **Третий системный баг: `Promise.all([...]).then(...)` без `.catch()` в ~10 файлах** (Home,
  Employees, Departments, Regulations, Projects, Clients, AbsenceRequests, Blog, EmployeeProfile).

  режиме сеть — обычное дело, и без `.catch()` страница застревала в `loading: true` навсегда при
  любом сбое запроса (ровно то, что пользователь увидел на чужом кабинете). Добавлен `.catch()`

### v0.2.6 — практичная проверка обновлений через сервер + аккордеон "Последние входы"
Пользователь обновил сервер до v0.2.5, у клиентов осталась v0.2.2, нажал "Проверить обновления" —
получил "Не удалось проверить обновления. Проверьте подключение к интернету..." (ожидаемо: настоящий
`tauri-plugin-updater` не настроен, см. большой комментарий в начале `src/lib/updater.ts` и запись
v0.1.1) и спросил, как это исправить. Предложены два варианта: полноценный автообновитель (ключ
подписи + публикация релизов, значительный объём работы) или практичная проверка версии через уже
существующий свой сервер — пользователь выбрал второй.

- **`src-tauri/src/main.rs`** — новая команда `get_app_version()`, возвращает
  `env!("CARGO_PKG_VERSION")` — версию ИМЕННО того процесса, который отвечает на вызов. Это ключевой
  трюк: в режиме клиента `invoke()` уходит на сервер (см. `api.ts`), значит вызов этой команды в
  клиентском режиме возвращает версию СЕРВЕРА, а не свою — без этого трюка узнать версию сервера было
  бы нечем. Зарегистрирована в `generate_handler!` и в `dispatch.rs` (`"get_app_version" =>
  Ok(to_json(crate::get_app_version()))`).
- **`src/lib/updater.ts`** — `UpdateCheckResult` получил новый вариант `{ status: 'server-newer';
  version }` (без `install` — доставить настоящий подписанный инсталлятор через этот канал
  невозможно, только сообщить). `checkForAppUpdate()` в начале проверяет `connection.isClient()`:
  если да — сравнивает `api.getAppVersion()` (версия сервера) с локальной `APP_VERSION` через новый
  `compareVersions()` (простое посегментное сравнение `x.y.z`, без внешних библиотек); если сервер
  новее — `server-newer`, иначе `up-to-date`. Настоящий `check()` из `@tauri-apps/plugin-updater`
  теперь вызывается только когда клиент НЕ в клиентском режиме (локально или сам сервер) — старое
  поведение (и вся оговорка про ключ подписи) там не изменилось.
- **`UpdatesButton.tsx`** (ручная проверка через Настройки/подвал) и **`UpdateNotifier.tsx`**
  (всплывающее окно при входе) — оба теперь понимают `server-newer`: кнопка показывает текст
  `updates.serverNewer`, модалка — отдельный экран с `updates.serverNewerTitle`/`serverNewerBody` и
  ТОЛЬКО кнопкой "Закрыть" (без "Обновить сейчас", т.к. install недоступен для этого статуса).
- **"Последние входы" в кабинете сотрудника — аккордеон по дням** (`EmployeeProfile.tsx`), по прямому
  запросу пользователя. Раньше — плоский список всех сессий с датой в каждой строке. Теперь сессии
  группируются по локальной дате (`localDateKey`, через `getFullYear/getMonth/getDate`, не
  `toISOString`, чтобы не съехать на день из-за UTC) в `sessionGroups`
  (`useMemo`). Каждая группа — сворачиваемый блок: заголовок = сама дата + счётчик записей + шеврон,
  по клику разворачивается/сворачивается (`dayOverrides` — только ручные переключения, дефолт
  вычисляется на лету: `dateKey === todayKey`). Сегодняшний день открыт по умолчанию, остальные
  свёрнуты — ровно как просил пользователь ("если день кончился — сворачивалось").

Не проверено вживую — `tsc`/`cargo check`/`vite build` чистые. Стоит проверить: реально ли
"Проверить обновления" в клиентском режиме честно сообщает о разнице версий (сервер v0.2.5+ vs
клиент со старой версией), и что аккордеон "Последние входы" разворачивается/сворачивается плавно

### v0.2.9 — реальное автообновление (скачивание с сервера) + брендинг установщика + Партнёры (второй
### этап) + харденинг вебвью + масштаб окна + переживание рестарта сервера

Самый большой батч за сессию — несколько независимых запросов пользователя подряд, без явной паузы
между ними. Порядок ниже — по теме, не по хронологии сообщений.

**1. Реальное автообновление в режиме клиента (скачивание установщика с сервера и запуск).**
Раньше (v0.2.6) "Проверить обновления" в режиме клиента честно сравнивало версию клиента с версией
сервера и только СООБЩАЛО, что на сервере новее — реального способа обновиться не было (настоящий
`tauri-plugin-updater` требует ключи подписи и публикацию в GitHub Releases — не настроено и не
входит в эту задачу). Пользователь подтвердил через AskUserQuestion пойти прагматичным путём: админ
вручную кладёт собранный установщик на машину-сервер, сервер раздаёт его по сети, клиент скачивает и
запускает — без проверки подписи (осознанный компромисс для доверенной офисной LAN, не интернета).
  - **`src-tauri/src/main.rs`** — `AppDataDir(PathBuf)` — новый managed-state, отдельный от
    `AppState(Mutex<Db>)` (чтобы не трогать сигнатуры ~90 существующих команд). `update_installer_path()`
    вычисляет путь `$APPDATA/updates/downloaded-installer.exe` — единое место, известное и Rust-, и
    JS-стороне. Команды `get_update_installer_info` (есть ли файл + размер) и `get_update_installer_path`
    (сам путь, для UI-подсказки админу). `.setup()` регистрирует `tauri_plugin_fs`/`tauri_plugin_shell`
    и прокидывает `app_data_dir` в `server::run(...)`.
  - **`src-tauri/src/server.rs`** — новый маршрут `GET /api/update-installer`, НЕ через общий
    `/api/invoke` (JSON) — установщик весит мегабайты, base64-в-JSON для такого объёма бессмысленный
    оверхед. Отдельный, простой ручной токен-чек (та же логика, что в `invoke_handler`, но без общей
    диспетчеризации) и `tokio::fs::read` сырых байт с `Content-Disposition: attachment`.
  - **`src-tauri/src/dispatch.rs`** — сигнатура `dispatch()` получила пятый параметр
    `app_data_dir: &Path` (нужен для двух новых команд); все ~90 существующих вызовов не изменились.
  - **Права доступа** — новая головоломка с Tauri v2 ACL, проверено чтением исходников крейтов в кэше
    cargo (интернета для официальной документации не было): `fs:default` даёт только
    `create/read-app-specific-dirs-recursive` — этого мало для записи файла, добавлены
    `fs:allow-appdata-write-recursive`/`read-recursive`/`meta-recursive`. `shell:default` — НЕ то, что
    кажется по названию: у него уже вшит собственный ограниченный `scope` (только `http(s)://`, `tel:`,
    `mailto:` — см. `tauri-plugin-shell-2.3.5/src/scope.rs`), локальный путь `.exe` он не пропустит.
    Взят `shell:allow-open` (без предустановленного scope на уровне capability) + `tauri.conf.json` →
    `plugins.shell.open: true` — валидация урла/пути у плагина отдельная от ACL-уровня, оба слоя нужны
    одновременно.
  - **`src/lib/updater.ts`** — статус `'server-newer'` теперь опционально несёт `install()` (если
    `getUpdateInstallerInfo()` подтвердил, что файл реально лежит на сервере) — скачивает через
    `@tauri-apps/plugin-http`'s `fetch` с заголовком токена, сохраняет через `@tauri-apps/plugin-fs`'s
    `writeFile` в `$APPDATA/updates/...`, запускает через `@tauri-apps/plugin-shell`'s `open()`. Новая
    `quitApp()` (через `tauri-plugin-process`'s `exit(0)`) — ОТДЕЛЬНО от существующей `restartApp()`

    установщик заменяет .exe целиком — текущий процесс должен полностью выйти, а не релончнуться.

**6. Читаемость на тёмных темах — корневая причина, не точечный патч.** Пользователь показал скриншот
тёмной темы: цифры в плитках статистики на Главной и текст задач ("2", сырая внутренняя ссылка
`tauri.localhost/#entry-...`) были едва видны — почти чёрным текстом на тёмном фоне. Причина — все эти
элементы лежат внутри `<button>` (`.home-stat-tile`, `.home-task-row`), а у нативного `<button>`
браузерный дефолт — системный цвет текста, а НЕ `currentColor`/наследование от родителя, если явно не
переопределено. У этих конкретных кнопок `color` нигде не был задан. Вместо точечного фикса под каждый
класс — общее правило `button, select { color: inherit; font-family: inherit; }` сразу после `* {
box-sizing: border-box; }` в начале `theme.css`: специфичность класса (`.primary`, `.modal-btn.danger`
и т.д.) выше, так что все места, где цвет уже задан явно, продолжают работать как раньше — это только
safety-net на случай, когда цвет забыли задать (как в этом случае).

**7. Клиент переживает рестарт сервера без потери места и без непонятной ошибки.** Токены сессий на
сервере живут только в памяти (`ServerState.sessions`) — перезапуск сервера-процесса разлогинивает
всех клиентов молча: следующий сетевой вызов от клиента получал 401 "Не авторизован — войдите заново"
и просто падал с общей ошибкой загрузки на текущей странице, без объяснения, что происходит, и без
возврата туда же после повторного входа. Пользователь явно попросил и понятное объяснение, и
восстановление места.
  - **`src/lib/sessionExpiry.ts`** (новый) — простая шина событий (`notifySessionExpired`/
    `onSessionExpired`) — низкоуровневая `invoke()` в `api.ts` не может сама решить, что показать
    пользователю и куда его вести, поэтому просто оповещает.
  - **`src/lib/api.ts`** — в клиентской ветке `invoke()`: если `result.error` совпадает ровно со
    строкой, которую `server.rs::unauthorized()` всегда возвращает при отсутствующем/невалидном
    токене — это однозначно означает "сессия на сервере больше не существует" (единственный источник
    этой конкретной строки), а не обычную ошибку конкретной команды — вызывается `notifySessionExpired()`.
  - **`src/lib/returnPath.ts`** (новый) — `saveReturnPath()`/`consumeReturnPath()` (одноразовое чтение
    из `localStorage`, чтобы обычный последующий вход не утаскивал на случайно оставшийся путь).
  - **`src/App.tsx`** — подписка на `onSessionExpired`: запоминает текущий `location.pathname`
    (`saveReturnPath`), сбрасывает локальную сессию, выставляет флаг `sessionExpiredNotice`. Экран
    `/login` при следующем успешном входе (`setCurrentEmployee`) считывает сохранённый путь
    (`consumeReturnPath`) и редиректит именно туда (`<Navigate to={returnPath ?? '/dashboard'} replace
    />`), а не всегда на дашборд с нуля.
  - **`src/pages/Login.tsx`** — новый необязательный проп `sessionExpired` — показывает отдельный
    поясняющий блок над формой входа (`.session-expired-notice`, новый CSS), а не просто молчаливый
    редирект на пустой экран логина.
  - Ограничение (осознанное, не забытое): восстанавливается только МАРШРУТ (какая страница/карточка
    была открыта), а не буквально несохранённый ввод в форме (например, недописанный текст в
    текстареа) — полное посимвольное восстановление черновиков избыточно рискованно для этой задачи
    и не было тем, о чём просил пользователь буквально.
